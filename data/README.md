# 銀行資料維護指南

`banks.ts` 是整個網站唯一的資料來源。這份文件說明資料模型長什麼樣、為什麼長這樣，以及要改的時候該怎麼改。

## 資料來源

PTT Bank_Service 板的年度總整理文：<https://www.ptt.cc/bbs/Bank_Service/M.1767533701.A.974.html>

原文會持續被原作者編輯（多半是半年一次的活動換檔）。`references/` 保留了每次更新當下的快照：

| 檔案 | 內容 |
|---|---|
| `bank.txt` | 原文內文純文字 |
| `bank-new.png` / `bank-old.png` | 新戶／舊戶懶人包表格 |
| `bank-rule-*.png` | 個別銀行的分級或任務規則圖 |

**懶人包表格是彙整結果，不是規則本身。** 遇到數字對不起來時（例如將來銀行的 1.6875% 是跨級距加權後的值），以內文與規則圖為準。

## 資料模型

```ts
interface BankRateInfo {
  rate: number;          // 排序與計息用的數值，單位是「百分比」，2.1 代表 2.1%
  display: string;       // 畫面上顯示的文字，通常是 '2.100%'
  quota: string;         // 額度的顯示文字，例如 '20萬'、'不限'
  numericQuota: number;  // 這一列能吃下的金額上限，無上限用 Infinity
  transfers: string;     // 跨轉／跨提優惠次數
  notes: string;         // 條件、期間、級距等補充說明
}

interface BankData {
  id: string;                            // 列的唯一鍵，同一家銀行拆多列時用 '<code>-tierN'
  name: string;                          // 顯示名稱
  code: string;                          // 銀行代碼，「是否持有」以 code 為單位
  newCustomer: BankRateInfo;             // 未持有時套用
  newCustomerTaskNotMet?: BankRateInfo;  // 未持有且未達任務時套用
  oldCustomer: BankRateInfo;             // 已持有時套用
  oldCustomerTaskNotMet?: BankRateInfo;  // 已持有但未達任務時套用
}
```

`id` 與 `code` 的分工是關鍵：**配置演算法逐 `id` 計算，但使用者的「已持有／考慮申辦」勾選是逐 `code` 記錄的。** 所以把一家銀行拆成多列時，每列的 `code` 必須相同，`id` 必須不同——勾一次就會同時啟用該銀行的所有級距列。

## 配置演算法

`App.tsx` 的作法是單純的貪婪配置：

1. 依 `rate` 由高到低排序（已持有／考慮申辦的排在前面）
2. 由上而下，每一列吃 `Math.min(剩餘金額, numericQuota)`
3. 吃完就往下一列

三個直接後果，改資料前要先知道：

- **`rate` 決定順序，`numericQuota` 決定份量。** 兩者都要填對，否則配置結果會錯。
- **同一家的級距列彼此獨立排序**，中間可以夾進其他銀行。這是正確行為：2.1% 那一段本來就該跟其他 2.1% 的銀行競爭。
- **`numericQuota: Infinity` 的列會吃光剩餘資金。** 只有真的無上限（樂天舊戶、Bankee 舊戶）才這樣寫，否則「未配置餘額」會永遠顯示 0。

演算法沒有「優惠期間」的概念，年利率一律當成整年計算。像王道新戶 12% 只有 1 個月，實際年化效果遠低於表面數字——這類限制寫在 `notes` 讓使用者自行判斷。

## 怎麼拆級距

當一家銀行的利率隨金額分段時（王道、將來、陽信…），拆成多列，每列代表一段。

**拆點取新戶與舊戶所有級距邊界的聯集。** 新舊戶共用同一組列，如果只照其中一邊的邊界拆，另一邊就會算錯。

以王道 O-Bank 為例，它實際上是兩個活動疊加：

| 活動 | 對象 | 內容 |
|---|---|---|
| 他轉專案 | 新舊戶皆可 | 20萬內 2.1%、20~100萬 1.5% |
| 新戶好禮 | 首次開立帳戶者 | 10萬內 12%，為期 1 個月 |

舊戶的邊界是 `20萬 / 100萬`，新戶多一條 `10萬`。聯集後得到 `10萬 / 20萬 / 100萬`，於是拆成三列：

| `id` | 級距 | `newCustomer` | `oldCustomer` |
|---|---|---|---|
| `048-tier1` | 0~10萬 | 12% × 10萬 | 2.1% × 10萬 |
| `048-tier2` | 10~20萬 | 2.1% × 10萬 | 2.1% × 10萬 |
| `048-tier3` | 20~100萬 | 1.5% × 80萬 | 1.5% × 80萬 |

每列的 `numericQuota` 填的是**這一段的寬度**，不是累積上限。三列相加，新舊戶都剛好是 100 萬。

只照舊戶邊界拆成兩列（`20萬 / 80萬`）的話，新戶的 10~20 萬那段會被誤算成 1.5%，而且 1.5% 的 80 萬會提早從第 10 萬開始吃。

`name` 建議帶上級距（`王道 O-Bank (10~20萬)`），否則畫面上同一家出現三次會看不懂。

## 常見情境怎麼寫

**舊戶完全沒有優惠**（元大、凱基）：`rate: 0`、`display: '無優惠'`、`numericQuota: 0`。額度 0 讓配置演算法直接跳過這一列，畫面也會隱藏額度條。

**要解任務才有高利率**（聯邦、臺企銀、陽信、彰銀）：主欄位填達成後的值，再補一個對應的 `*TaskNotMet` 填未達成的值。使用者在設定或卡片上切換，畫面會把兩者一起顯示。

新舊戶各有各的 fallback，兩邊獨立：`newCustomer` 配 `newCustomerTaskNotMet`，`oldCustomer` 配 `oldCustomerTaskNotMet`。只填其中一邊也可以——沒填的那一邊就不顯示開關。判準是**那一邊的優惠是否真的綁任務**：例如彰銀新戶 2.5% 是無條件的固定優惠，就不該有 `newCustomerTaskNotMet`。

任務狀態本身是逐 `code` 記錄的單一狀態，不分新舊戶。切換成「已持有」或「考慮申辦」以外的狀態時會自動清掉。

**任務影響的是額度而不是利率**（上海）：一樣用 `*TaskNotMet`，只是兩者差在 `numericQuota` 而非 `rate`。上海的基本限額是 20 萬，解加碼條件後次月起 30 萬——新舊戶都適用，所以兩組 fallback 都要填。

**利率是牌告加碼**：`rate` 填算好的結果，`notes` 保留公式（`'牌告 + 0.36%'`），下次牌告變動時才知道要重算什麼。

## 更新流程

1. 抓原文與圖：`curl -H 'Cookie: over18=1' <PTT 網址>`，圖片網址在內文裡
2. 把新的內文與圖覆蓋到 `references/`，`diff` 舊版找出哪些銀行真的有變
3. 依 diff 改 `banks.ts`；只有懶人包表格變、內文沒變的地方要回頭確認是哪一邊過期
4. 更新 `App.tsx` footer 的「更新：YYYY/MM/DD」為原文最後編輯日（`※ 編輯:` 那行）
5. `npm run build` 確認過關
6. 推上 `main`，GitHub Actions 會自動部署
